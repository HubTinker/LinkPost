# Undefined chat_id в Long Polling при message_created

**Date:** 2026-06-07 17:40
**Files:** poll.js, api/index.js, lib/max-api.js
**Severity:** critical

## Problem

При запуске Long Polling (`npm run poll`) бот отправлял десятки запросов к MAX API с `chat_id=undefined`, получая ошибку 400. Это забивало лимит запросов (rate limit) и делало бота нерабочим.

Лог: `[FIX] API request POST /messages?chat_id=undefined {"text":"❌ Ключ не найден..."}` и `[FIX] API error 400 {"code":"proto.payload","message":"Failed to convert value: 'undefined'"}`

## Root Cause

В `poll.js` `chat_id` извлекался только с верхнего уровня апдейта: `const { chat_id, user } = update`. Однако Long Polling API для `message_created` не гарантирует `chat_id` на верхнем уровне — он может быть вложен в `update.message.chat_id` или `update.chat?.chat_id`. В результате `chat_id` был `undefined`, и все вызовы `sendMessage(undefined, ...)` проваливались.

Дополнительно не было:
- Защитной проверки `chat_id` перед вызовом `sendMessage`
- Валидации обязательного параметра в `sendMessage`

## Solution

1. **poll.js** — извлечение `chat_id` с fallback: `update.chat_id || update.message?.chat_id || update.chat?.chat_id`. Если `chat_id` всё равно отсутствует — апдейт пропускается с предупреждением.
2. **api/index.js** — добавлен guard в `handleMessage`: если `chat_id` нет, функция завершается досрочно.
3. **lib/max-api.js** — добавлена валидация `chatId` в `sendMessage` и `sendMessageWithLink` с явным `throw` при отсутствии.

## Prevention

- При работе с Long Polling API всегда обрабатывать вложенные форматы данных
- Добавлять защитные проверки на обязательные поля перед вызовом API
- При разработке на локальном polling сначала логировать структуру апдейта
