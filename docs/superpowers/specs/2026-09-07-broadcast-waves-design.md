# Спецификация: Рассылка «волнами» — лимит получателей и память доставок

Дата: 2026-09-07 · Статус: дизайн согласован, готов к плану реализации

## 1. Цель

Админ может запустить рассылку не всем, а на ограниченный контингент (пресеты 100/200/500/1000 или введённое число) — «пробная волна». Повторный запуск той же рассылки («Разослать ещё») доставляется только тем, кто её ещё не получал: память «кто получил» хранится навсегда **в рамках рассылки**. Волны идут в детерминированном порядке: старейшие подписчики первыми.

## 2. Ключевые решения

| Решение | Выбор |
|---|---|
| Память доставок | Только в рамках одной рассылки (`broadcast:<id>:sent` — источник правды). Новая рассылка с другим текстом снова идёт всем |
| Порядок получателей | Старейшие первыми: `first_seen` ↑, `undefined` → 0, тайбрейк `user_id` ↑ |
| Ввод лимита | Гибрид: пресеты 100/200/500/1000 + «Свой вариант» (число 1–10000) + «Всем» (`limit = null`) |
| Механика | «Детерминированная очередь»: движок на каждом батче пересчитывает список ещё не получивших |
| Упавшие пользователи | Вариант Y: внутри запуска не повторяем (`:run_attempted`), в новом запуске пробуем снова |
| Отсчёт прогресса | `_run_sent_at_start`: на старте записываем `scard(:sent)`; стоп при `scard(:sent) − _run_sent_at_start >= limit` |
| Сброс run-состояния | Только при явном старте админом (выбор числа). Не на хопах цепочки, не при stop/resume |

## 3. Модель данных

### 3.1 Запись рассылки `broadcast:<id>` — новые поля

- `limit` — число | `null`. Лимит текущего запуска; `null` = «Всем» (стоп только по исчерпанию кандидатов).
- `_awaiting_limit` — boolean. «Ждём число от админа» (режим «Свой вариант»).
- `_run_sent_at_start` — число. `scard(:sent)` на момент старта текущего запуска (точка отсчёта S).

Все три поля добавляются в whitelist `updateBroadcast` (`lib/broadcast.js`), иначе патчи молча отбрасываются.

### 3.2 Новый KV-ключ

`broadcast:<id>:run_attempted` — set user_id, уже обработанных в **текущем** запуске (успех или ошибка). Заменяет хрупкий курсор-индекс: безопасно переживает цепочку HTTP-вызовов.

Хелперы в `lib/broadcast.js` (рядом с `markSent`):
- `markRunAttempted(bid, userId)` — sadd;
- `getRunAttempted(bid)` — smembers → JS `Set`;
- `clearRunAttempted(bid)` — del.

### 3.3 Очистка ключей

- `deleteBroadcast` и `resetBroadcastStats` дополнительно удаляют `:run_attempted` (иначе после удаления/сброса останется мусор, и новый запуск подхватит чужое run-состояние).
- `:cursor` движком больше не используется (игнорируется, принудительно не удаляем). Старые незавершённые рассылки «самолечатся» на следующем батче.

## 4. Движок отправки — `lib/broadcast-runner.js`

Единая функция `runBroadcastBatch(bid, batchSize = 20)` для обоих путей отправки: инлайн-старт с кнопки и `/process-broadcasts` (цепочка/cron). Дублирование батч-логики из `api/index.js` (две копии) устраняется.

### 4.1 Выбор получателей (пересчёт на каждом батче)

1. `getAllUsers()` → сортировка `first_seen` ↑ (`undefined` → 0), тайбрейк `user_id` ↑.
2. Один раз `smembers(:sent)` и `smembers(:run_attempted)` → JS `Set`. Никаких `sismember` в цикле (2N лишних команд на батч недопустимы).
3. Кандидат = не `inactive` && не в `:sent` && не в `run_attempted`. Упавшие в **прошлых** запусках (`:failed`, но не в `run_attempted`) — кандидаты (Y: повторяем).

### 4.2 Лимит и размер пачки

- `S = scard(:sent) − _run_sent_at_start` — доставлено в текущем запуске.
- Фолбэк: если `_run_sent_at_start` отсутствует/undefined (старая/граничная запись) — принять за точку отсчёта текущий `scard(:sent)` (исключает NaN в стоп-условии).
- Guard `limit == null` («Всем»): стоп только по исчерпанию кандидатов, сравнение с лимитом не выполняется.
- Эффективная пачка = `min(batchSize, limit − S)`, выход из цикла сразу при `S >= limit` (на последней пачке не улетает «до 20 лишних»).

### 4.3 Отправка

- Успех: `markSent`, `markDelivered`, `markRunAttempted`, S инкремент.
- Ошибка: `markFailed`, `markRunAttempted` (внутри запуска не повторяем; лимит не тратится). 404/`chat.not.found`/`dialog.not.found` → `markInactive` (выпадает из выборки).
- Пауза между отправками `BATCH_DELAY` (50 мс) — как сейчас.

### 4.4 Конкурентный guard

В начале батча `status = 'sending'`, по итогам — `'sent'` (завершено) или `'scheduled'` с `scheduled_at = now + 1000` (продолжение). Закрывает гонку «cron наложился на выполняемый батч» (`getScheduledBroadcasts` фильтрует только `scheduled`). Инлайн-старт использует тот же runner (сейчас в `confirm_now` guard'а нет — старый race, чинится).

### 4.5 Идемпотентность

Двойная доставка исключена комбинацией: статус `sending` + фильтр `getScheduledBroadcasts` + `run_attempted`.

## 5. UI-поток

### 5.1 Экран «Кому отправляем?»

Открывается из: предпросмотра рассылки («✅ Отправить»), «▶️ Запустить» у черновика, «📤 Разослать ещё» у `sent`/`cancelled`.

Текст: предпросмотр + `👥 Уже получили: X` (`scard(:sent)`) · `📭 Ещё не получали: M` (кандидаты нового запуска: не sent, не inactive; упавшие включены — по Y) · `🚫 Неактивных: K`.

Кнопки: `[100] [200] [500] [1000] [Свой вариант] [Всем] [🔙]`.

При `M = 0`: кнопки чисел не показываются, старт невозможен, текст «📭 Нет новых получателей — все уже получили эту рассылку.»

### 5.2 «Свой вариант»

- Кнопка → `_awaiting_limit = true` (у остальных рассылок админа флаг снимается — одновременно ожидать может только одна), ответ «Введите число получателей (1–10000).»
- В `handleMessage`, **до** ветки черновика: `getAllBroadcasts().find(b => b._awaiting_limit && b.created_by === userId)` — поиск вне зависимости от статуса (`getActiveDraft` ищет только `draft` и «Разослать ещё» на `sent`/`cancelled` не перехватил бы — это был блокер).
- Валидное целое 1–10000 → запуск (п. 5.3). Невалидное → «Введите число от 1 до 10000», флаг остаётся.
- Флаг снимается: при старте, на «🔙 Назад» экрана получателей, при открытии другого `broadcast_view` или другого экрана получателей.

### 5.3 Старт запуска

1. Проверка статуса: только `draft` / `sent` / `cancelled`. При `scheduled`/`sending` — отказ «Сначала остановите текущую отправку.»
2. `updateBroadcast`: `status='scheduled'`, `scheduled_at=Date.now()`, `created_by_chat_id=chatId`, `limit = n | null`, `_awaiting_limit=false`, `_run_sent_at_start = scard(:sent)`.
3. `clearRunAttempted(bid)` — **единственная** точка сброса run-состояния.
4. Первый батч инлайн через `runBroadcastBatch`, затем цепочка `/process-broadcasts` (как сейчас).

### 5.4 Кнопки деталей рассылки

| Статус | Кнопки |
|---|---|
| `draft` | ✏️ Редактировать · ▶️ Запустить |
| `scheduled` / `sending` | ⏸ Остановить |
| `cancelled` | ▶️ Возобновить · 📤 Разослать ещё |
| `sent` | 📤 Разослать ещё |
| все | 📊 Статистика · 🗑 Удалить |

- «▶️ Возобновить» (`cancelled`) = **тот же** запуск: `status='scheduled'`, `scheduled_at=now`; `run_attempted` не трогаем; число не спрашиваем; продолжается к исходному лимиту; упавшие внутри запуска не повторяются.
- «📤 Разослать ещё» (`sent`/`cancelled`) = **новый** запуск: экран получателей → п. 5.3; `run_attempted` обнуляется, новый `_run_sent_at_start`; упавшие прошлых запусков повторяются (Y).
- «🔄 Перезапустить» удаляется: сценарии покрыты (in-flight → stop/resume; завершённая → «Разослать ещё» с памятью). Полный «разослать всем заново» сознательно не предусмотрен — противоречит гарантии «никому дважды»; при необходимости добавится отдельной guarded-кнопкой позже.

### 5.5 Прогресс, детали, статистика

- Детали (`broadcast_view`), in-flight: `📤 Запуск: S / L` (S = `scard(:sent) − _run_sent_at_start`; при «Всем» — «S из M»), `❌ Ошибок за запуск: …`.
- Завершение: `status='sent'` + итог админу: `✅ Получили: N всего (в этот запуск S) · ❌ Ошибок: … · 🚫 Пропущено неактивных: …`.
- `broadcast_stats`: строка `в этом запуске: S, лимит: L | <все>`.
- Прогресс-сообщения каждые 15 доставок (как сейчас) — с S/L.
- Тест-кнопка «🔍 Тест» и поток создания (текст → картинки → кнопки) не меняются.

## 6. Обработка ошибок

- Ошибки отправки: см. 4.3.
- Обрыв цепочки (fetch не дошёл): рассылка остаётся `scheduled` (`now + 1000`) → подхват cron'ом/следующим вызовом; runner идемпотентен.
- KV-сбой в runner: лог + рассылка остаётся `scheduled` → повторится (как фатальные ошибки сегодня).

## 7. Тестирование

### 7.1 Хранилище (`test/broadcast.test.js`)

- `markRunAttempted` / `getRunAttempted` / `clearRunAttempted` — roundtrip.
- `deleteBroadcast` и `resetBroadcastStats` удаляют `:run_attempted`.
- `updateBroadcast` сохраняет `limit`, `_awaiting_limit`, `_run_sent_at_start`.

### 7.2 Runner (новый `test/broadcast-runner.test.js`)

- Порядок: `first_seen` ↑, `undefined` → 0, тайбрейк `user_id`.
- Фильтрация: исключены sent / inactive / run_attempted; упавшие прошлых запусков включены.
- Лимит: стоп по достижению; ошибки не расходуют квоту; `null` → до исчерпания; пачка `min(20, остаток)`; «лишних» на последней пачке нет.
- Y: упавшие повторяются в новом запуске.
- Guard: `sending` в начале батча, восстановление `scheduled`/`sent`.
- Фолбэк `_run_sent_at_start` undefined.
- `_run_sent_at_start` переживает stop/resume (S не сбрасывается).

### 7.3 Обработчики (`test/handler.test.js`)

- Предпросмотр → экран получателей.
- Пресет-старт и цепочка; «Всем».
- «Свой вариант»: валид → старт; невалид → повторный запрос; «🔙 Назад» снимает флаг.
- **Регрессия блокера: `sent` (или `cancelled`) → «Разослать ещё» → «Свой вариант» → ввод числа → запуск стартовал** (перехват вне черновика).
- Повтор на `sent`: память сохраняется, повторных доставок нет.
- `cancelled`: «Возобновить» — без дублей и без запроса числа; «Разослать ещё» — новый запуск.
- `M = 0`: старт невозможен.
- Запрет старта при `scheduled`/`sending`.
- Прогресс/детали/статистика с S/L.

### 7.4 Обновить существующие

- Тесты экранов прогресса/статуса — новые тексты.

## 9. Миграция

Не требуется: `:cursor` игнорируется; run-ключи создаются заново при старте; незавершённые рассылки «самолечатся» (`:sent` точен, упавшие прошлых запусков повторятся).

## 10. Вне области

- Глобальная память «хоть раз получил любую рассылку» (вариант Б — отклонён пользователем).
- Полный повторный сброс «разослать всем заново» (противоречит памяти).
- Изменение тест-кнопки и потока создания рассылки.
