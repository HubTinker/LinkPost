# Дизайн: навигация в терминальных сообщениях команд

**Дата:** 2026-08-13  
**Статус:** Утверждён  
**Скоуп:** 8 точек в `api/index.js` + утилита + тесты

---

## 1. Проблема

После успешного выполнения команд (`/setlink`, загрузки изображения в рассылку) и при ошибках валидации бот отправляет «тупиковое» сообщение — без inline-кнопок для дальнейших действий. Пользователь вынужден вспоминать команды или искать предыдущее меню.

## 2. Инварианты архитектуры (не нарушаем)

- `renderScreen` — единая точка рендера навигационных экранов, правит `nav_msg` на месте.
- **Команды всегда отправляют новые сообщения** (коммит `1d28e6e`). Не редактируем `nav_msg` из команд.
- Колбэки на кнопках любого сообщения получают `editMsgId` и рендерят следующий экран **в том же сообщении** через `renderScreen`.
- Новых колбэков/обработчиков не добавляем — используем существующие (`links`, `create`, `back`, `broadcast_menu`, `broadcast_images_done`).

## 3. Решение: паттерн `sendCommandResult`

Вводим единую утилиту для терминальных сообщений команд:

```js
/** Терминальное сообщение команды: ряд действий + строка «Назад» */
async function sendCommandResult (chatId, text, actions = [], backData = 'back') {
  const rows = []
  if (actions.length) {
    rows.push(actions.map(a => ({ type: 'callback', ...a })))
  }
  rows.push([{ type: 'callback', text: '🔙 Назад', data: backData }])
  return sendMessageWithKeyboard(chatId, text, rows)
}
```

Параметры:
- `actions` — массив `{ text, data }` для верхнего ряда (основные действия).
- `backData` — payload для кнопки «Назад» (по умолчанию `'back'`; для рассылки — `'broadcast_menu'`).

## 4. Точки изменения (8 штук)

| # | Место | Текущее поведение | Новое поведение |
|---|-------|-------------------|-----------------|
| 1 | `/setlink` успех (L375–382) | `sendMessage`, тупик | `sendCommandResult` с actions: `[{text:'📋 Связки',data:'links'}, {text:'➕ Создать ещё',data:'create'}]` |
| 2 | `/setlink` неверный формат (L354–357) | `sendMessage`, тупик | `sendCommandResult` без actions (только `[🔙 Назад]`) |
| 3 | `/setlink` невалидный URL (L363) | `sendMessage`, тупик | `sendCommandResult` без actions |
| 4 | `/setlink` длинный ключ (L366) | `sendMessage`, тупик | `sendCommandResult` без actions |
| 5 | `/setlink` длинный URL (L369) | `sendMessage`, тупик | `sendCommandResult` без actions |
| 6 | `/dellink` ключ не найден (L389) | `sendMessage`, тупик | `sendCommandResult` без actions |
| 7 | `/dellink` нет прав (L391) | `sendMessage`, тупик | `sendCommandResult` без actions |

> Примечание к строке 7: ветка недостижима через команды (не-админ отсечён на L345–348, админ всегда проходит `canManage`). Меняем для консистентности — тот же паттерн ошибки жив в callback-флоу `del:` для создателей-не-админов, и при изменении фильтра команд ветка не станет тупиком.
| 8 | Рассылка: «📷 Изображение добавлено» (L483) | `sendMessage`, тупик | `sendCommandResult` с actions: `[{text:'✅ Готово',data:'broadcast_images_done:<id>'}]`, `backData: 'broadcast_menu'` |

### Почему нет ветки не-админа в `/setlink`

`/setlink` для не-админа молча игнорируется на L345–348 — до сообщения успеха код не доходит. Ветка `isAdmin ? adminButtons : userButtons` была бы мёртвым кодом.

### Почему `back`, а не `create`, в ошибках

Единый инвариант: *ошибка команды → 🔙 Назад → главное меню*. Текст ошибки формата уже содержит пример, поэтому «К инструкции» избыточен. Это масштабируется на любую будущую команду без специфичных payload'ов.

## 5. Что не трогаем (сознательно)

- `renderScreen`, `lib/nav.js`, KV-логика `nav_msg` — не затрагиваем.
- `/stats`, `/users` — просмотр данных, не флоу добавления/удаления контента.
- `/links` пустой список для не-админа — `back` для не-админа ведёт в подсказку, кнопка бесполезна.
- Подтверждение `/dellink` (Да/Нет), шаг 1 рассылки, предпросмотр, `confirm_del`, `broadcast_clear_stale` — уже с кнопками.
- `showLinkCard` не используем как замену сообщению успеха — теряется «➕ Создать ещё», добавляется связность.

## 6. Техдолг

**5 изображений = 5 сообщений с кнопками.** При загрузке нескольких картинок подряд каждая порождает новое сообщение «📷 Изображение добавлено». Это clutter. В будущем можно хранить `last_image_msg_id` в draft и редактировать предыдущее сообщение вместо отправки нового (edit-in-place). Пока оставляем ради простоты.

## 7. Тесты

### Обновить существующие

- `/setlink should create a link for admin` — добавить проверку `attachments[0].type === 'inline_keyboard'`, 2 ряда кнопок, payload'ы `links`, `create`, `back`.
- 4 теста ошибок `/setlink` — добавить проверку кнопки с payload `back`.
- 1 тест ошибки `/dellink` (`warn on missing key`) — добавить проверку кнопки с payload `back`. Ветка «нет прав» теста не имеет (недостижима через команды, см. примечание к строке 7) и новый тест для неё не пишем.

### Добавить новый

- «Изображение добавлено» — создать draft через `createBroadcast({ text, created_by: 123 })`, вызвать `handleMessage` с вложением-картинкой, проверить кнопки `broadcast_images_done:<id>` и `broadcast_menu`.

### Регрессия

- `npm test` целиком — `render-screen.test.js`, `nav.test.js` не затрагиваем, должны пройти без изменений.

## 8. Риски и митигация

| Риск | Митигация |
|------|-----------|
| Кнопки на сообщении успеха редактируют его вместо `nav_msg` — `nav_msg` указывает на старый экран | Приемлемо: `nav_msg` обновится при следующем `renderScreen` без `editMsgId`. Старые экраны в истории — уже существующее поведение. |
| `sendMessageWithKeyboard` логирует payload в консоль | Оставляем как есть (существующий `console.log` в `lib/max-api.js`). |
| Не-админы теоретически могут увидеть кнопки, которых не должны | Все затронутые команды (`/setlink`, `/dellink`, рассылка) доступны только админам. Payload'ы (`links`, `create`, `back`) уже в allowlist для не-админов, конфликтов нет. |
